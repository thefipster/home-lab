# Uptime Kuma Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add Uptime Kuma to the infra VM as a standalone stack at `uptime.thefipster.de` — the lab's notification layer, watching routed services end-to-end through Traefik and every container's state through the Docker API.

**Architecture:** One container, one external network (`proxy`), two bind mounts (its own data dir and `docker.sock`). No `.env`, no generated secrets, no database. No existing stack is modified — reaching unexposed containers is solved through the Docker API, not network topology.

**Tech Stack:** Uptime Kuma 2 (`louislam/uptime-kuma:2`), Traefik v3 (existing wildcard cert), hosted ntfy.sh for notifications.

**Spec:** [`docs/superpowers/specs/2026-07-26-uptime-kuma-design.md`](../specs/2026-07-26-uptime-kuma-design.md)

## Testing model (read first — this repo has no unit-test harness)

Correctness is verified by config validation plus review, as in every prior phase. Locally available and confirmed working: `docker compose config -q` (Docker Compose v5.1.4), `bash -n` for script syntax, Python 3.12 for YAML parsing. **The real proof is on the VM** — the container comes up, the route resolves with the wildcard cert, the Docker socket test succeeds, and stopping a container produces an ntfy push. That runtime sequence is the guide's checklist, written in Task 2 and executed by the operator, not by the implementer.

## Verified facts (checked, do not re-litigate)

- **`louislam/uptime-kuma:2` exists** on Docker Hub — a bare major tag, currently resolving to 2.4.0. Confirmed against the registry tag list. No major.minor or full-patch exception needed.
- **Kuma's HTTP port is 3001.**
- **Kuma's data directory is `/app/data`.**
- **The default image runs as root**, so `/opt/uptime-kuma` needs no `chown` (same as Alloy, unlike every other monitoring dir).
- **No compose file in this repo sets `container_name`.** Every container is `<project>-<service>-1`. Project names come from the `name:` key: `traefik`, `authentik`, `forgejo`, `monitoring`. `infra/dockge/compose.yaml` has **no `name:` key**, so its project is the directory `init-dockge.sh` copies it to — `/opt/stacks/dockge` — giving `dockge-dockge-1`.
- **`otlp.thefipster.de` has no root route.** Its two Traefik routers match `PathPrefix(/v1/)` and `PathPrefix(/opentelemetry.proto.collector.)` only, so a bare `GET /` returns a Traefik 404.
- **`dockge.thefipster.de` and `traefik.thefipster.de` are forward-auth gated** and answer 302 to Authentik, not 200.
- **`grafana-setup.md` currently ends the guide chain** ("The infra VM is complete") and states "Alerts are UI-only. Nothing is delivered anywhere yet." Both become wrong with this change.

## Global Constraints

Copied from `CLAUDE.md` and the spec; every task's requirements implicitly include these.

- **Image pin `louislam/uptime-kuma:2`** — major-only, per repo policy.
- **No IP literals** in the guide or the init script. Everything is addressed by DNS name; `docs/dns-records.md` stays the only place IPs are written down.
- **No SSO.** No `middlewares: authentik@docker` label, no outpost router. `infra/authentik/compose.yaml` is **not** modified. The deviation is documented in the compose header and in `sso-applications.md`, never silent.
- **No per-router TLS labels** — the single wildcard cert covers every `websecure` router.
- **No changes to any existing stack's compose or networks.** `monitoring-net` and `authentik-net` stay internal.
- **No `.env` and no `.env.example`** — Kuma has nothing to seed.
- **Init script house style:** `set -euo pipefail`, paths from `$BASH_SOURCE`, the shared `run_root()` helper, re-runnable, runnable from anywhere.
- **The ntfy topic is a bearer secret.** It is generated by the operator and lives only in Kuma's SQLite — never committed, never written into a guide as a literal.
- **Line endings: LF**, and `*.sh` must stay LF (CRLF breaks the shebang).
- **Grafana's alert rules are not touched.** Kuma owns outbound notification; no Grafana contact point is added.

- [ ] **Step 1: Create `infra/uptime-kuma/compose.yaml`**

The header comment carries the two things a reader will look for and not find anywhere else: why this is not part of the monitoring stack, and why there is no forward-auth label.

```yaml
# Uptime Kuma — independent black-box monitoring for the INFRA VM.
#
# Deliberately its OWN stack, not part of infra/monitoring. That stack is a
# white-box PIPELINE (Alloy collects -> Prometheus/Loki/Tempo store -> Grafana
# displays) living inside everything it watches. Kuma is black-box and only
# works from OUTSIDE: in the same compose project, one `docker compose down` on
# monitoring would take out the pipeline AND the thing that tells you the
# pipeline is down. It also covers a blind spot that stack documents about
# itself — if Alloy dies, `up` goes stale, the ServiceDown rule evaluates
# NoData -> OK, and nothing fires for the most total failure there is.
#
# Division of labour, so the two never grow into each other:
#   Kuma    -> notices and NOTIFIES (ntfy). The thing that pokes you.
#   Grafana -> metrics, logs, traces, dashboards. The thing that explains why.
# Grafana's alert rules stay UI-only ON PURPOSE — adding a contact point there
# would mean duplicate alerts for the same conditions and two places to tune.
#
# NO SSO, and that is a DELIBERATE DEVIATION from the repo convention (every
# other UI joins Authentik by OIDC or forward-auth). Kuma has no OIDC, so the
# convention would point at forward-auth — but gating the outage dashboard
# behind the identity provider makes an Authentik outage the one failure you
# cannot see, and the break-glass path (comment the middleware, recreate) needs
# SSH at exactly the moment you are already firefighting. Kuma ships real local
# auth (bcrypt, optional 2FA) and the lab is LAN-only, so the exposure is
# bounded. Recorded in docs/sso-applications.md as an intentional
# non-integration. infra/authentik/compose.yaml is untouched by this stack.
#
# Deploy (on the infra VM): scripts/init-uptime-kuma.sh, then bring it up —
# see docs/uptime-kuma-setup.md, which also carries the monitor inventory
# (monitors live in Kuma's SQLite, so the guide is what makes them
# reproducible).

name: uptime-kuma

services:
  uptime-kuma:
    # Major-only pin, per repo policy. Verified against the registry: a bare
    # `2` tag IS published (unlike alloy/tempo, which need a full patch pin).
    image: louislam/uptime-kuma:2
    restart: unless-stopped
    volumes:
      # SQLite, uploads, and every monitor/notification definition. Kuma is
      # self-contained — no separate database service, and nothing here is
      # provisioned from the repo (see the guide's monitor inventory).
      # The default image runs as ROOT, so this dir needs no chown — same as
      # Alloy, unlike the rest of the monitoring tree.
      - /opt/uptime-kuma:/app/data
      # Docker API — this is what lets Kuma report the state of containers it
      # shares NO network with (Authentik's db/redis/worker, Loki, Prometheus,
      # Tempo). It is why this stack needs no network changes anywhere else.
      # The fourth socket mount in the lab, after Dockge, Traefik and Alloy,
      # and it carries the same caveat: `:ro` makes the MOUNT read-only, NOT
      # the API behind it. This is root-equivalent control of the VM's Docker.
      # Acceptable only because this is a single-tenant box.
      - /var/run/docker.sock:/var/run/docker.sock:ro
    labels:
      traefik.enable: "true"
      traefik.http.routers.uptime.rule: Host(`uptime.thefipster.de`)
      traefik.http.routers.uptime.entrypoints: websecure
      traefik.http.services.uptime.loadbalancer.server.port: "3001"
      # Deliberately NO middlewares label — see the header. Kuma does its own
      # login, and gating it behind Authentik would hide Authentik outages.
    networks:
      # `proxy` only. Kuma does NOT join monitoring-net or authentik-net:
      # container state comes from the socket above, and the routed services
      # are checked over HTTPS through Traefik — the real user path, which is
      # the more honest black-box signal anyway.
      - proxy

networks:
  proxy:
    external: true
```

- [ ] **Step 3: Create `scripts/init-uptime-kuma.sh`**

Modelled on `scripts/init-monitoring.sh`, minus everything about secrets and ownership. Note the closing message names the host, never an IP.

```bash
#!/usr/bin/env bash
#
# init-uptime-kuma.sh — project-specific setup for the Uptime Kuma stack.
#
# Assumes Docker is installed (run scripts/init-host.sh first). Steps:
#   1. Create the persistent data dir at /opt/uptime-kuma.
#   2. Ensure the shared `proxy` network exists.
#   3. Symlink the stack into /opt/stacks so Dockge can manage it.
#
# There is NO .env and nothing to generate — Kuma has no database and creates
# its admin account through its own first-run web form. That makes this the
# shortest init script in the repo, and the only stack without a .env.example.
#
# No chown either: the default image runs as root (like Alloy, unlike the rest
# of the monitoring tree, where each image drops to a different UID).
#
# Re-runnable: every step is idempotent. Run from anywhere.
# Usage (from the repo root):
#   scripts/init-uptime-kuma.sh

set -euo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
REPO_ROOT="$(cd "${SCRIPT_DIR}/.." && pwd)"
STACK_DIR="${REPO_ROOT}/infra/uptime-kuma"

run_root() {
  if [ "$(id -u)" -eq 0 ]; then
    "$@"
  else
    sudo "$@"
  fi
}

if ! command -v docker >/dev/null 2>&1; then
  echo "docker not found — run scripts/init-host.sh first." >&2
  exit 1
fi

echo "==> Creating the persistent data dir at /opt/uptime-kuma"
run_root mkdir -p /opt/uptime-kuma

echo "==> Ensuring the shared 'proxy' network exists"
docker network inspect proxy >/dev/null 2>&1 || docker network create proxy

STACKS_DIR="${STACKS_DIR:-/opt/stacks}"
echo "==> Linking the stack into ${STACKS_DIR}/uptime-kuma (for Dockge)"
run_root mkdir -p "${STACKS_DIR}"
run_root ln -sfn "${STACK_DIR}" "${STACKS_DIR}/uptime-kuma"

echo
echo "Done. Next (see docs/uptime-kuma-setup.md):"
echo "  1. Verify the uptime.thefipster.de host record resolves to the infra"
echo "     VM — the registry is docs/dns-records.md. The *.thefipster.de"
echo "     wildcard points at the APPS VM, so without an exact record the"
echo "     name hits the wrong box and returns a 404 behind a valid cert."
echo "  2. cd ${STACK_DIR} && docker compose up -d"
echo "  3. Open https://uptime.thefipster.de and create the admin account."
echo "     There is NO Authentik login in front of this — that is deliberate;"
echo "     see docs/sso-applications.md."
```

`## Troubleshooting` — the five failure modes from the spec, each with its one-line check:

- **Kuma unreachable and Traefik logs nothing** → missing DNS record; the name fell through the wildcard to the apps VM. `getent hosts uptime.thefipster.de`.
- **Every Docker monitor fails with a connection error** → socket mount missing or the Docker Host path is wrong. `docker compose exec uptime-kuma ls -l /var/run/docker.sock`.
- **A Docker monitor is red but the container is running** → name mismatch. `docker ps --format '{{.Names}}'`.
- **HTTP monitor red with a TLS error** → almost always the guest clock after a snapshot rollback, which `init-host.sh` addresses at the chrony level; the same failure mode as every other TLS client in the lab.
- **Monitor went red but no ntfy push** → topic mismatch, or the notification was never attached to that monitor ("Default enabled" was not ticked).

`## Layout on the server` — `/opt/uptime-kuma` (SQLite + uploads), `/opt/stacks/uptime-kuma` → symlink to the repo, and the explicit note that **monitors and notifications live in the SQLite, not in the repo** — which is exactly why the inventory table above is the reproducible record.

`## How it works` — below-the-fold rationale: why standalone rather than part of monitoring (fate-sharing defeats black-box monitoring; the dead-Alloy blind spot); why no SSO and what that trades away; why the socket rather than joining `monitoring-net`; why hosted ntfy.sh rather than self-hosted (self-hosting on this VM would share fate with everything it reports on); and the limitation stated plainly — **Kuma runs on the infra VM and dies with it**, so it catches a stack failing, the common case, and not the VM failing.
